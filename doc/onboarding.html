gis (Ghost In the Shell)

Gas Town を徹底的に削ぎ落とした、決定論的マルチAIエージェント・オーケストレーション環境。
beads で管理された課題を git worktree で分離されたエージェント（Claude Code / Codex CLI）に並列で配り、機械検証と相互レビューを通過したものだけを直列にマージします。

⚡ Deterministic Dispatch 🛡️ Git Worktree Isolation 🔒 Serial Rebase Merge Queue

1 gis とは？（全体概要）

AIコーディングエージェント（Claude Code や Codex CLI）の自律的な開発能力を活用しつつ、 「コンフリクトでコードが壊れる」「エージェントが無限ループする」「勝手に危険な変更をマージする」といった並列開発特有の破綻を、 決定論的なルールとサンドボックス構造で完全に防ぐためのオーケストレーションツールです。

🏷️

Beads による課題管理

DoltベースのGit互換チケットシステム bd を使用。依存関係グラフと優先度から「今着手すべき作業」が決まります。

🌿

Worktree による完全分離

1つのチケット（Bead）ごとに専用の git worktree を作成。エージェント同士が同じディレクトリで衝突することはありません。

🚦

直列マージキュー

実装完了したブランチは1本ずつ順番に main を rebase し、再度テストを実行して合格したものだけをマージします。

2 設計思想 & 核の3要素

gis の最大の特徴は「複雑さを意図的に捨てる」哲学にあります。先行する大規模エージェントフレームワーク（Gas Townなど）が抱えていた過度な抽象化や運用の難しさを排し、実用上本当に必要な3つだけに機能を絞り込みました。

🎯 gis が担う「3つの核」

  1. ワークツリー分離した並列ワーカー: 各AIエージェントに独立した作業場を与える
  2. beads からの決定的な work dispatch: LLMにタスク配分を任せず、決定論的ロジックで配る
  3. マージ順序の直列化: 複数ブランチの同時合流による破損をゼロにする

Gas Town から意図的に捨てたもの

なぜ捨てたのかの理由を知ることで、gis のコードベースがなぜここまで簡潔に保たれているかが分かります。

捨てたもの 理由・gis での代替手段
常駐監視エージェント (Deacon/Witness等) 「エージェントの不調をエージェントで直す」はデバッグ不能。プロセス状態検知は herdr のポーリングで十分。
常駐デーモン 「デーモンが死んだ」「二重起動」「ログ迷子」等の運用問題を生む。gis run をフォアグラウンドループとして動かす。
エージェント間通信 (mail/broadcast) 直列パイプライン（実装 → 検証 → レビュー → マージ）で十分代替できる。
独自語彙 (rig/refinery/polecat) 認知負荷の温床。一般名詞（worktree, worker, reviewer, merge queue, gate）のみを使う。
複数リポジトリ横断 複雑さの元凶。単一リポジトリ前提とし、別ディレクトリで起動すれば90%足りる。

💡 なぜエージェントの stdout を読まないのか？
エージェントは PTY（仮想端末）上で対話モードで動作します。gis は画面の文字出力をスクレイピングするのではなく、 ファイルシステム経由（.gis/run/implement-prompt.md や .gis/run/round-1-impl.json）のみで通信します。 これにより、UIの微小な変更で壊れる「画面読みパース」を根本的に排除しています。

図 4-1: Bead 1件のライフサイクル・シーケンス
1
ディスパッチ & プロファイル解決
bd ready --exclude-label human から最優先のタスクを決定論的に取得。タスク種別（epic/decisionなら plan、通常は implement）から適切なAIモデル（Claude / Codex）を選択。
2
ワークツリー作成 & エージェント起動
.worktrees/{bead-id} に独立したブランチを展開。.gis/run/implement-prompt.md に要件を書き込み、herdr 経由でエージェントを立ち上げます。
3
Verify ループ（安価な機械検証を先行）
高価なAIレビューの前に、pnpm check（型チェック、lint、単体テスト、slop検査）を実行。失敗時は同一ペイン（文脈保持のまま）にエラーログを投げて修正させます。
4
Review ループ（異ベンダ相互レビュー）
Claudeが書いたコードはCodexが、Codexが書いたコードはClaudeがレビュー。同一レビュアーが最後まで見守るため、指摘が発散せず確実に収束します。
5
直列マージキュー
1ブランチずつ順番に main を rebase → コミット差分が存在するか確認 → verify 再実行 → 合格なら merge & bd close。

5 深掘り: 堅牢性を支える仕組み

🛡️ 5.1 人間確認ゲート (Human Checkpoint Gate)

エージェントに「重要な判断の手前で止まれ」とプロンプトで指示しても、無視して進んでしまうリスクがあります。gis ではこれをBeads の依存関係グラフで構造的に強制します。

⚠️ なぜエージェントに直接 bd を触らせないのか？
エージェントに bd を操作させると、自分でゲートを作ったり、自分自身のステータスを書き換えてゲートを回避できてしまいます。そのため bd への書き込みは gis のみが独占します。

🔄 5.2 3者照合によるクラッシュ復旧

gis run を実行中に Ctrl-C で中断したり、OSが強制終了された場合でも、次回起動時に「3者照合」を一回行うだけで完全に回復します。

Herdr Pane Git Worktree Beads Status 復旧アクション
❌ なし ❌ なし 🟡 in_progress open に戻す（次回ディスパッチで再実行）
❌ なし 🌿 あり 🟡 in_progress blocked に倒す（worktreeパスを記録し人間へ引き継ぎ）
🖥️ あり - ❌ なし / closed 人間に報告して放置（勝手に消さない）

🧹 5.3 コード品質ゲート (gis slop)

AIエージェントが生成しがちな「コードの重複（Redundancy）」や「無駄な構造肥大（Structural Erosion）」を merge-base と比較して静的解析します。

  • Redundancy: 正規化された3行ブロックの重複コード比率
  • Structural Erosion: 複雑度10超の関数が占める割合（cyclomatic complexity * sqrt(SLOC)）

gis slop では、これらの指標が 0.02 (2%) を超えて悪化した場合にゲートが遮断されます。

7 新人向け実践ワークフロー

新人が gis リポジトリで作業を開始する際の手順とコマンド集です。

1. 環境セットアップ

Terminal
# Node.js 22+ & pnpm の有効化
corepack enable
pnpm install

# 全体チェック (Lint, Format, Test, Typecheck, Slop)
pnpm check

2. Beads によるタスクの確認

Terminal
# 着手可能なチケットの一覧表示
bd ready

# チケットの詳細確認
bd show <bead-id>

# チケットの作成
bd create --title="機能の追加" --description="..."

# 人間確認用ゲートの作成
bd create --labels human --title="設計レビュー承認"
🚨 重要: Beads 操作時の鉄則
  1. bd create に --parent を渡さない: ID採番の競合を防ぐため、作成後に bd update $ID --parent=<epic> で紐付けます。
  2. bd dolt push は DOLT_REMOTE_INFO_BRANCH="" で実行: 余分な追跡ブランチが作られるのを防ぎます。

3. gis の実行

Terminal
# オーケストレータの起動 (フォアグラウンドで実行)
gis run

# 設定の初期化 (対話ウィザード)
gis init

# コード品質レポートの確認
pnpm slop:report

4. blocked になった時の引き継ぎ手順

エージェントが自力で解決できず blocked になった場合、チケットの notes に「3点セット」が記録されます。

📋 引き継ぎの3点セット

  1. Worktree パス: .worktrees/{bead-id}（手動で入ってコードを確認・修正）
  2. ラウンドログ: .gis/run/round-*.json（エージェントとレビュアーの応酬履歴）
  3. トランスクリプトパス: Claude/Codex の詳細実行ログ

8 開発規約・品質基準

項目 コマンド / 規約 説明
フォーマッタ pnpm format (oxfmt) 高速な Rust 製フォーマッタ。コミット前に自動適用。
リンター pnpm lint (oxlint) --deny-warnings で警告ゼロを強制。

テスト pnpm test (node:test) Node.js 組み込みのテストランナーで TypeScript ビルド後を実行。
フルチェック pnpm check Format + Lint + Typecheck + Test + Slop Report の一括検証。
